# BRC-212: Wrapped UTXOs from Foreign Chains

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Held back. Submitted as [#336](https://github.com/bsv-blockchain/BRCs/pull/336) and withdrawn on 2026-10-18 until coins of other chains are ready to propose.

## Abstract

A wrapped token is a BSV token whose units stand for coins held on another proof-of-work chain, such as Litecoin or Bitcoin. Someone deposits a UTXO on that chain to a public reserve script. The issuer then mints the same number of base units on BSV, naming the deposit in the minting transaction.

This document defines how every reader checks that backing for itself. A deposit's burial proof is the raw deposit transaction, its merkle path and its block header. Each reader checks it against its own header chain of the foreign chain, which it syncs from explorers it does not trust. A unit's state is a function of that chain alone:

- **Waiting.** The deposit has fewer than 6 confirmations on the reader's chain. The unit is credited but cannot move.
- **Movable.** The deposit has at least 6 confirmations on the reader's chain.

There is no stored lock, no issuer attestation and no timer. A deposit that is double-spent before it is buried leaves units that never become movable, so nobody downstream can ever receive them.

The document also defines chain profiles for Litecoin and Bitcoin, how proofs travel with transfers, redemption, and what a wallet must show so users can tell a wrapped token from an issued one.

## Motivation

Wallets that hold tokens claiming to be backed by another chain usually trust a bridge operator, an oracle or an indexer for the claim. The claim that matters most, that a real deposit exists and is buried, can be checked by anyone with the deposit's merkle proof and a header chain.

Two shortcuts break that check:

1. **Headers carried in the proof.** A proof that brings its own run of headers proves only that someone did that much work. On a chain like Litecoin, a few headers at low difficulty cost far less than the value they would unlock. Requiring more headers for more value only moves the break-even point.
2. **Locks the issuer lifts.** If units wait for the issuer to attach or sign something, they depend on the issuer being live. They also leave a "pending" state with its own rules, timers and failure modes.

This document removes both. The reader's own chain is the only judge of burial. A unit's state is computed from that chain each time it is needed.

## Relationship to other documents

- [HCT backed tokens](./hct-backed-tokens.md) (withdrawn from BRC-255 §15) is the reference binding: the deploy field `bk` names the chain and reserve, and each mint carries an `hctb` backing output naming its deposit. Any token format can bind this document the same way (§1).
- [BRC-67](https://github.com/bsv-blockchain/BRCs/blob/master/transactions/0067.md) (SPV) describes the same check for BSV itself. Here the chain being checked is foreign, so the reader keeps that chain's headers itself.
- [BRC-45](https://github.com/bsv-blockchain/BRCs/blob/master/tokens/0045.md) defines UTXOs as tokens. A wrapped unit is a BSV UTXO token whose issuance names a foreign UTXO.

## Terms

- **Foreign chain:** the proof-of-work chain that holds the reserve, identified by a chain id from §6 (`"ltc"`, `"btc"`).
- **Reserve script:** the locking script on the foreign chain that deposits pay. It is fixed when the asset is created.
- **Reserve holder:** whoever can spend the reserve script. Usually this is the issuer, alone or as a federation.
- **Deposit:** one output on the foreign chain that pays the reserve script and backs one issuance.
- **Issuance:** a BSV transaction that writes new units of a wrapped asset (a deploy or a mint).
- **Burial proof:** the evidence that a deposit is in a block (§3).
- **Reader:** any wallet that validates the asset, whether it is a holder, a recipient or an auditor.
- **Reader's chain:** the reader's own header chain of the foreign chain (§5).
- **Depth `D`:** the confirmations a deposit needs before its units move. `D` is 6 for every profile in §6.

## Specification

### 1. Binding

A token format binds this document by guaranteeing four things in its own signed transactions:

1. **Immutable basis.** The asset's creation fixes its chain id and its reserve script, and nothing can change either later. In the [HCT binding](./hct-backed-tokens.md) this is the deploy field `bk: { chain, reserve }`.
2. **One deposit per issuance.** Every issuance names exactly one deposit outpoint (foreign txid and output index) inside the transaction that writes the units, so the issuer's signature covers it. In the HCT binding this is the single `hctb` backing output.
3. **Unit ratio.** One unit is one base unit of the foreign chain (a litoshi, a satoshi). An issuance writes at most the deposit's value.
4. **Holding rule enforced by validation.** The format's validation (for BRC-255, the §7 walk) refuses to accept units that an issuance wrote unless the reader holds a burial proof of that issuance's deposit that checks under §4. No script enforces this: every reader does.

A reader MUST refuse an issuance that names a deposit already named by another issuance of any wrapped asset it has validated with the same chain id and reserve script.

### 2. Unit state

A reader computes each unit's state from its own chain whenever it needs it:

| State | Condition on the reader's chain | Reader behavior |
|---|---|---|
| Waiting | The deposit is not yet in a block, or it is in one with fewer than `D` confirmations | Credit the unit, show it as waiting with "n of D confirmations", and never spend it |
| Movable | The deposit's block is on the reader's chain with at least `D` confirmations | Spend and accept normally |

Rules:

1. A reader MUST NOT store a lock, flag or timer that overrides the condition above. The state is always derived again from the reader's chain.
2. A unit can only become movable. It never returns to waiting, because a burial at depth `D` is a fact about the foreign chain that the reader keeps (§5).
3. A wallet MUST NOT spend a waiting unit, and MUST NOT include one in a transfer, an offer or a swap.
4. A deposit that leaves the foreign chain's mempool, or is double-spent before it is buried, leaves its units waiting forever. A wallet MAY present such units as abandoned after a period it chooses. That label is presentation only: nothing can prove a deposit will never confirm, and nothing needs to, since the units already cannot move.

Only the wallet that received the issuance ever holds waiting units. Every other reader sees units only after they move, and by then they are movable on the sender's chain. Each reader checks them again on its own chain.

### 3. Burial proof

A burial proof is a JSON object:

```json
{
  "tx": "<raw deposit transaction, hex>",
  "path": ["<merkle sibling, display hex>", "..."],
  "pos": 0,
  "height": 3196930,
  "header": "<80-byte header of the deposit's block, hex>"
}
```

- `tx` is the deposit transaction serialized **without** witness data.
- `path` lists the merkle siblings from the leaf up, in display (big-endian) hex. It has at most 32 entries.
- `pos` is the transaction's index in the block.
- `height` is the block's height on the foreign chain.
- `header` is the block's 80-byte header.

The proof names a block. It carries no other headers, and it never goes stale.

### 4. Checking a proof

Given an issuance naming deposit `txid:vout`, issuing `n` units, under reserve script `R`, a proof checks when all of the following hold:

1. The double SHA-256 of `tx` equals `txid`.
2. `tx` is not a coinbase transaction, and it is not exactly 64 bytes long (a 64-byte transaction can pose as an inner merkle node).
3. Output `vout` of `tx` has a locking script byte-equal to `R` and a value of at least `n`.
4. Folding `txid` with `path` by `pos` (double SHA-256 of left‖right, internal byte order) yields the merkle root of `header`.
5. The block hash of `header` (double SHA-256 of the 80 bytes, for every profile in §6) is the hash at `height` on the reader's chain.
6. The reader's chain has at least `D - 1` blocks after `height`.

The result is one of three outcomes:

- **Buried:** all six checks pass. The issuance's units are movable.
- **Missing:** checks 1 to 4 pass, but the reader's chain cannot yet decide check 5 or 6, either because its tip is not `D - 1` past `height` or because it could not reach a header source. Missing is not failure: the reader keeps the units waiting, or keeps the received transfer pending, and checks again later.
- **Failed:** any of checks 1 to 4 fails, or the reader's chain is at least `D - 1` blocks past `height` and holds a different hash at `height`. The issuance's units are invalid for that reader.

A proof that fails because the foreign chain reorganized away a shallow block is missing, not failed, until the reader's chain is `D - 1` past that height.

### 5. The reader's chain

Each reader keeps a header chain of each foreign chain it reads. It trusts header bytes from any source only after checking them itself.

1. **Checkpoint.** The chain starts at a checkpoint the wallet ships: a height, its block hash, its bits and time, and the times the next retarget reads (§6). The checkpoint MUST be below the lowest deposit the reader will check. A wallet SHOULD keep it fixed below the first deposit of every wrapped asset it supports rather than move it up with releases, because a deposit below the checkpoint can only be reached by linking down by hash (rule 4).
2. **Forward headers.** A header after the tip is accepted only when:
   - it names the tip's hash as its previous block;
   - its bits are exactly what the profile's retarget rule gives at its height;
   - its proof-of-work hash, read as a 256-bit little-endian number, is at most the target its bits encode, and that target is at most the profile's proof-of-work limit;
   - its time is at most two hours after the reader's clock.
3. **Reorganizations.** When a source offers headers that branch below the tip, the reader accepts the branch only if every header on it passes rule 2 and the branch has more total work (the sum of 2^256 / (target + 1)) than the part of its chain the branch replaces. A reader MAY refuse branches deeper than 100 blocks.
4. **Below the checkpoint.** A block below the checkpoint is accepted only when a run of headers links it up to the checkpoint by hash. A reader MAY cap that run, and treats a deposit below the cap as missing.
5. **On demand.** A reader syncs only when a check needs a height or depth its chain does not have yet. A check whose block is already `D - 1` deep on the reader's chain needs no network.
6. **Storage.** A reader needs to keep only block hashes by height, plus the bits and times the next retarget reads. A reader MUST keep them across restarts: a burial it has seen at depth `D` stays buried.

A header source is anything that returns header bytes: a block explorer, a peer on the foreign chain's network, or a relay service. Sources only supply bytes, so a lying source can delay a check but can never make one pass.

### 6. Chain profiles

A profile fixes everything §3 to §5 need for one foreign chain:

| Field | Litecoin (`"ltc"`) | Bitcoin (`"btc"`) |
|---|---|---|
| Base unit | litoshi (10^-8 LTC) | satoshi (10^-8 BTC) |
| Transaction id | Double SHA-256 of the transaction without witness | Same |
| Block hash | Double SHA-256 of the 80-byte header | Same |
| Proof-of-work hash | scrypt(header, salt = header, N = 1024, r = 1, p = 1, 32 bytes) | Double SHA-256 of the header |
| Proof-of-work limit | 2^236 − 1 | 2^224 − 1 |
| Retarget interval | 2016 blocks | 2016 blocks |
| Target timespan `T` | 302400 s (3.5 days) | 1209600 s (14 days) |
| Window start time | time(h − 2017) | time(h − 2016) |
| Depth `D` | 6 | 6 |

**Retarget rule.** At a height `h` that is not a multiple of the interval, bits equal the previous header's bits. At `h ≡ 0 (mod 2016)`:

1. Set `span = time(h − 1) − window start time`, clamped to `[T / 4, 4T]`.
2. Set `target = previous target × span / T`, capped at the proof-of-work limit, and encode it in compact form.

For Litecoin, when the previous target's bit length exceeds 235, the target is shifted right by one bit before the multiplication and left by one bit after it, exactly as Litecoin Core does. The window start differs between the chains because Litecoin reads one block further back, which closes Bitcoin's off-by-one in the window.

**Litecoin MWEB.** Only canonical outputs are deposits. A peg-in to MimbleWimble extension blocks is not in the canonical transaction a burial proof hashes, so it can never be a deposit. A reserve script MUST NOT be an MWEB address.

**Other chains.** A chain gets a profile only when every field above is fixed. A merged-mined chain (for example, Dogecoin under AuxPoW) also needs its auxiliary proof-of-work rules in the profile. A chain whose difficulty adjusts every block needs the full algorithm, and the reader must keep whatever history that algorithm reads.

### 7. Transfers

A recipient's validation reaches every issuance in the history of the units it is offered, as the binding's format defines.

1. A sender SHOULD attach, with the transfer, the burial proof of every issuance the recipient's validation will reach that the sender does not know the recipient has already checked. In the HCT binding, proofs ride the transfer package under `bk`, keyed by issuing txid.
2. A recipient checks each proof per §4 against its own chain and keeps the proofs that pass. A deposit is checked once per reader.
3. A recipient missing a proof MAY fetch the deposit's merkle proof and header from any source and build the burial proof itself. The source is untrusted in the same way as in §5.

### 8. Redemption

1. A holder redeems by taking units out of circulation on BSV, as the binding's format allows (BRC-255 burns them to an unspendable lock, because it forbids destroying units). The redeeming transaction names the foreign destination script and the amount.
2. The reserve holder pays that amount, less the foreign chain's fee as the asset's terms state, from the reserve to the destination.
3. A reserve holder SHOULD pay out only from deposits that are buried at depth `D` on its own chain. Paying out from a waiting deposit risks paying for a deposit that is later double-spent.
4. A holder can check the payout with the same proof format and its own chain. The payout's burial proof, with `vout` naming the destination output, checks against the destination script instead of the reserve.

### 9. Reserve transparency (informative)

The reserve script is public, and so is every issuance and redemption. Anyone can add up deposits named by issuances, redemptions on BSV, and the reserve's balance on the foreign chain, and compare them. This document does not make the reserve holder keep the reserve. It makes the holder's failure to keep it visible to anyone who looks.

### 10. Presentation

A wallet that holds or offers wrapped units:

1. MUST show the asset's basis as "backed by `<foreign chain>`" and the reserve holder's identity (the issuer's identity key, resolved handle or certified name), next to the token's name everywhere the token appears: balances, send, receive, activity, offers and permission prompts.
2. MUST draw the foreign chain's mark from the asset's chain id. It MUST NOT let issuer-supplied metadata (icon, name, ticker) supply or imitate that mark, and it MUST NOT show the mark for an asset whose basis is not wrapped.
3. MUST tell apart two assets with the same name or ticker by their reserve holder.
4. MUST show waiting and movable amounts separately, with "n of D confirmations" for waiting units, and MUST offer only movable units for spending.
5. MUST NOT describe a burial proof as evidence that the reserve still holds the deposit. A proof shows that a deposit was made and buried. Whether the reserve still holds it depends on the reserve holder.
6. SHOULD show a fiat or foreign-coin estimate only for movable units.
7. MUST ask the user to confirm explicitly before any action that moves the foreign chain's coins, such as a redemption or a conversion from a legacy unbacked asset. Such an action MUST NOT run automatically.

### 11. Compute budget (informative)

- A header is 80 bytes. Litecoin produces 576 a day, so a reader that stores only hashes needs about 18 KB a day of history. Bitcoin produces about 144 a day.
- One scrypt evaluation at N = 1024 costs a fraction of a millisecond on a phone. A day of Litecoin headers checks in well under a second.
- A reader syncs only when a check needs it. A wallet that holds only movable units it has already checked never touches the network for this document.
- A long first sync is the main cost for a new reader whose checkpoint is far behind the tip. A header source that serves headers in bulk (thousands per request) reduces it, without adding trust.

## Security considerations

- **Reserve trust.** A reader trusts the reserve holder to keep the reserve and to honor redemptions. No reader can enforce that. A federation of `m`-of-`n` keys (`m ≥ 2`, `2m > n`) means no single stolen key empties the reserve.
- **No trust in existence or burial.** A reader trusts neither the issuer nor any explorer that a deposit exists, pays the reserve, or is buried. To forge a burial, an attacker must put a block on the chain with the most work in the reader's own chain. That takes majority hash power on the foreign chain, or an eclipse of every source the reader uses plus enough real proof of work to outpace the foreign chain from the checkpoint.
- **Depth.** Six confirmations is where a reorganization of Litecoin or Bitcoin stops being practical for an attacker without majority hash power. Units below that depth cannot move, so a double-spent deposit costs only the depositor's own unmovable units.
- **Checkpoint.** A wrong checkpoint is a wallet bug, not a remote attack. Readers that ship different checkpoints still agree on any block their chains share.
- **Clock.** The two-hour future rule depends on the reader's clock. A clock far behind delays sync. It cannot make a forged header pass proof of work.
- **Merkle ambiguity.** The 64-byte and coinbase exclusions in §4 close the known ways to pass an inner node or an immature output as a deposit.
- **Double issuance.** An issuer that mints one deposit twice inflates supply. §1 makes readers refuse a second issuance naming a deposit they have already seen. An issuer that shows each issuance only to different readers can still do it. §9 makes that visible to anyone who checks.
- **Lookalikes.** A token can copy another's name and icon. It cannot copy the asset id or the reserve holder's identity. §10 makes wallets show the reserve holder and keep the chain mark for real wrapped assets.

## Rationale

**The reader's chain, not the proof's headers.** A proof that carries headers costs an attacker only the work in those headers. A proof that names one block, checked against the reader's own chain, costs the attacker the work of the whole foreign chain since the checkpoint.

**A fixed depth.** Depth that scales with value was there to make carried headers expensive. Once readers keep their own chain, extra headers add no security. A single `D` per profile matches what each chain's own users treat as final.

**State derived, not stored.** A stored lock needs someone to lift it, and a timer needs agreement on time. Deriving the state from the reader's chain gives every reader the same answer for the same block, with no issuer online and no extra state to sync.

**Credit at first sight.** The depositor sees the units immediately, and they cannot move until buried, so crediting early takes nothing from anyone downstream.

**No covenant.** A BSV script cannot see the foreign chain. Validation enforces the holding rule, which is enough: units moved early are worthless to every reader that validates.

## Open questions

1. **Bulk header relays.** A standard response format for serving thousands of foreign headers per request would shorten first syncs. It would still be trustless.
2. **Federated reserves.** A profile-independent way to name an `m`-of-`n` reserve holder and show it in §10.
3. **Proofs of liabilities.** A compact way for a reserve holder to commit to all issuances of an asset, so §9 does not need a full scan.
4. **More profiles.** BRC-213 §1 already fixes header rules for Bitcoin Cash (ASERT) and Dogecoin (AuxPoW, DigiShield). A profile here would adopt them and add a depth.

## Implementations

HandCash Desktop and Mobile implement the Litecoin profile for wLTC under the [HCT binding](./hct-backed-tokens.md) (retired in the wallet in favour of native LTC, BRC-213):

- `src/wallet/ltc/headers.ts` holds the reader's chain: a shipped checkpoint, exact retarget, scrypt proof of work, most-work reorganizations, linking down by hash, and storage of hashes only. Native coins (BRC-213) reuse it with each binding's rules (`src/wallet/{bch,btc,doge}/headers.ts`).
- `src/wallet/ltc/verify.ts` holds the burial proof and §4's check.
- Deposit, issuance and redemption lived in `src/wallet/wltc/bridge.ts`, removed with wLTC; `src/wallet/hct/backing.ts` still validates backed tokens already held.

Header bytes come from litecoinspace.org, with BRC-CLOUD's `/v1/ltc` route (litecoinspace, then Blockbook) as a fallback.
