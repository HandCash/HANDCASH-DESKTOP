# BRC-246: Session Upgrade

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

This BRC lets two online wallets move [BRC-33](https://bsv.brc.dev/peer-to-peer/0033.md) messagebox traffic onto a direct IPv6 socket. One wallet sends a signed, short-lived endpoint offer through the messagebox. The other dials it, and both sign a handshake. Later messages in that session skip the store-and-forward hop.

The messagebox remains the rendezvous and the offline inbox. The socket carries the same message bodies the box would and never carries custody.

## Motivation

A messagebox exists because the other wallet is often offline, firewalled, or unable to keep a listener. When both wallets are online, routing every chat line and remittance card through a store-and-forward host adds latency for nothing.

Dialing first and falling back to the box stalls a send on a filtered port. This BRC races a short dial against the box, fails through at once when the connect is refused, and keeps the endpoint out of handle records.

## Specification

### Scope

This BRC covers messages already sent over BRC-33: chat, remittance cards, and similar notices. It does not cover coin selection, signing, or broadcast. An on-chain output remains the only proof of payment or item custody.

Out of scope: IPv4, NAT traversal, hole punching, and publishing an endpoint in [BRC-169](https://bsv.brc.dev/peer-to-peer/0169.md) resolve.

### Signatures

Every signature in this BRC is ECDSA on secp256k1 by the signer's identity key, over SHA-256 of the UTF-8 preimage, with low-S. It is encoded as 64 bytes (`r ‖ s`, each 32 bytes big-endian) in lowercase hex. Preimages join their fields with `\n` and have no trailing newline.

### Endpoint offer

An offer is a UTF-8 message body:

```
handcash-session-offer:{"v":1,"host":"2001:db8::1","port":3342,"identityKey":"<hex>","counterparty":"<hex>","expiresAt":0,"nonce":"<32 hex>","signature":"<128 hex>"}
```

| Field | Rule |
|---|---|
| `v` | `1`. |
| `host` | Global unicast IPv6 (`2000::/3`), lowercase, no zone index. Link-local, ULA, multicast, loopback, and IPv4-mapped addresses MUST be rejected. |
| `port` | Integer 1–65535. |
| `identityKey` | Signer's compressed public key, lowercase hex. |
| `counterparty` | Compressed public key of the only identity allowed to dial, lowercase hex. MUST differ from `identityKey`. |
| `expiresAt` | Unix milliseconds, at most 60 seconds after signing. |
| `nonce` | 16 bytes from a cryptographically secure source, lowercase hex. |
| `signature` | Over the offer preimage. |

Offer preimage:

```
session-upgrade
offer
{identityKey}
{counterparty}
{host}
{port}
{expiresAt}
{nonce}
```

A wallet MUST send an offer only in a BRC-33 `sendMessage` body addressed to `counterparty`, and only while it has a listener bound to `host`/`port` that accepted a local test connection. It MUST NOT put an offer in a handle record, a BRC-169 resolve response, or any public directory. A wallet whose listener stops MUST stop sending offers.

A receiver MUST ignore an offer, and MUST NOT display it as chat, when any of these hold:

* `counterparty` is not the receiver's identity key.
* The signature does not verify against `identityKey`.
* `expiresAt` has passed, or is more than 60 seconds in the future.

Receivers MAY allow 5 seconds of clock skew on the expiry checks.

### Dialer

The identity whose key sorts lower as lowercase hex is the dialer. The other identity only listens, so a pair never opens two sockets.

### Race

When the dialer has an unexpired offer and no live session, it sends each message as follows:

1. Connect to `host`/`port` with a budget of 300 ms, measured from the start of the connect to a verified `welcome`.
2. If the connect fails with `ECONNREFUSED`, `ENETUNREACH`, `EHOSTUNREACH`, `EADDRNOTAVAIL`, `ENOTFOUND`, or `ECONNRESET`, discard the offer and send the message through the messagebox at once.
3. If the budget runs out, send the message through the messagebox. The dialer MUST NOT also send it on the socket, but MAY keep a session that completes later for the next message.
4. If the handshake completes within the budget, send the message on the socket only.

### Framing

Each frame is a 4-byte big-endian length followed by that many bytes of UTF-8 JSON. A receiver MUST close the socket on a frame of length 0 or over 256 KiB. A message whose frame would exceed 256 KiB MUST go through the messagebox.

### Handshake

The dialer sends `hello`:

```json
{ "t": "hello", "offer": <the offer object>, "speaker": "<hex>", "timestamp": <unix ms>, "nonce": "<32 hex>", "signature": "<128 hex>" }
```

Hello preimage:

```
session-upgrade
hello
{speaker}
{offer.identityKey}
{offer.host}
{offer.port}
{offer.nonce}
{nonce}
{timestamp}
```

The listener MUST verify the offer as a receiver would, except that `offer.identityKey` MUST equal the listener's own identity key. It MUST also check that `speaker` equals `offer.counterparty` and that the hello signature verifies against `speaker`. It then answers with `welcome`:

```json
{ "t": "welcome", "speaker": "<hex>", "timestamp": <unix ms>, "nonce": "<32 hex>", "helloNonce": "<32 hex>", "signature": "<128 hex>" }
```

Welcome preimage, where `peer` is the hello's `speaker` and `host`/`port` come from the offer:

```
session-upgrade
welcome
{speaker}
{peer}
{host}
{port}
{helloNonce}
{nonce}
{timestamp}
```

The dialer MUST check that `speaker` equals `offer.identityKey`, that `helloNonce` equals the nonce of its hello, and that the signature verifies. Both sides MUST reject a `timestamp` more than 60 seconds from their own clock, and a `nonce` that is not 32 hex characters.

### Messages

After a verified `welcome`, each message to that identity is one frame:

```json
{ "t": "msg", "id": "<id>", "body": "<the body the messagebox would have carried>" }
```

The receiver MUST pass `body` to the same ingest path as a messagebox message, and acknowledge it after ingest accepts it:

```json
{ "t": "ack", "id": "<id>" }
```

If the sender receives no `ack` within 300 ms, it MUST close the session and send that message through the messagebox. After a socket closes, messages go through the messagebox until a new offer completes a new handshake.

### What this is not

* Not a replacement for BRC-33. First contact, offline peers, and failed dials use the messagebox.
* Not a custody channel. An `ack` is not a payment.
* Not device sync. A session joins two identity keys, not two installs of one key.
* Not a listener requirement. A wallet that cannot listen never sends offers and can still dial.

## Security considerations

* **Endpoint exposure.** An offer reveals a reachable IPv6 address to one counterparty for at most 60 seconds. Wallets SHOULD NOT send offers to identities the user has not chosen to talk to.
* **Transport.** This BRC does not encrypt the socket or sign individual frames. The handshake authenticates which identities opened it. Each `body` relies on the same envelope protection it would have on the messagebox, so a body that is unsafe on the box is unsafe here.
* **Replay.** Offers expire within 60 seconds and are bound to one counterparty. Each hello and welcome signs fresh nonces and the other side's nonce.
