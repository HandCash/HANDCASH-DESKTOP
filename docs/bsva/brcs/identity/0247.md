# BRC-247: Sigma Identity

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

A Sigma identity is an on-chain persona derived from a [BRC-100](https://bsv.brc.dev/wallet/0100.md) wallet. It is not the wallet root, and it is not a [BRC-169](https://bsv.brc.dev/peer-to-peer/0169.md) handle.

The persona key is a public [BRC-42](https://bsv.brc.dev/key-derivation/0042.md) child. Publishing it inscribes a lean document and leaves a control output. Spending that control output revokes the persona. It does not rotate the root key and it does not release the handle.

1Sat and BSV-21 outputs that ask for the persona carry a VIN-bound SIGMA BSM tail signed by that child. The asset envelope stays the asset. The tail is the issuer attestation.

## Motivation

Issuers need a key that can attest an inscription or a token deploy without placing the wallet root on chain, and without inventing a second identity protocol. Indexers should not need a vendor table. The wallet identity key, the persona id, and the inscription are enough.

## Specification

### Roles

| Thing | What it is |
|---|---|
| Root identity | BRC-100 identity key. Apps prove it with a [BRC-138](https://bsv.brc.dev/peer-to-peer/0138.md) signature. |
| BRC-169 handle | A `$handle` claimed on the root key. |
| Sigma identity | A BKDS child used to attest 1Sat and BSV-21 issuances. |

### Derivation

BRC-42 public path, security level 0, counterparty `anyone`:

- `protocolID`: `[0, "sigma identity"]`
- `keyID`: persona id, or `<id>:<generation>` after a rotation
- Invoice: `0-sigma identity-<keyID>`

Anyone with the wallet identity key and the path can reconstruct the public key. Only the root holder can derive the private key. The root is never inscribed.

Persona id: `^[a-z0-9][a-z0-9-]{0,31}$`. It MUST NOT start with `sigma-`.

### Basket

Active persona outputs live in basket `sigma-<id>`. That name MUST NOT be `default`, `1sat`, `bsv21`, `index`, or `1sat-ft`. Coin selection MUST NOT spend a control output as cash or as a collectable. A pay balance MUST exclude `sigma-*`.

### On-chain layout

A persona document is a 1-satoshi output:

```
<persona P2PKH>
OP_FALSE OP_IF
  "ord"
  OP_1 "application/sigma-identity+json"
  OP_0 {"v":1,"id":"studio","name":"Studio"}
OP_ENDIF
OP_RETURN
  {"p":"sigma-identity","op":"publish","id":"studio"}
  |
  SIGMA
  BSM
  <signing address>
  <signature>
  0
```

The document JSON is `{ "v": 1, "id", "name", "about"? }`. Name is at most 40 characters. About is at most 80. No control characters.

The OP_RETURN metadata in front of the `|` is `{ "p": "sigma-identity", "op": "publish"|"rotate"|"revoke", "id" }`. Generation is omitted when it is 0.

The SIGMA tail is [SIGMA](https://bsv.brc.dev) algorithm `BSM`. The VIN field is the ASCII decimal of a concrete input index. `-1` MUST be refused. The signature covers the script in front of the `|` and commits to the outpoint at that input, so it cannot be replayed onto another spend.

Publishing is two transactions. Fund a 1-satoshi output in `sigma-<id>`, then spend it as input 0 to inscribe the document and leave a control output in the same basket. The control output is spendable only with the persona key. Unspent control means that generation is active. Spending it without a successor revokes the persona. The inscription remains as history.

### Asset attestation

The same tail MAY be appended to a 1Sat inscription or a BSV-21 deploy+auth output when that output asks for the persona (`sigma-identity:<id>`, or custom instructions `sigmaIdentity` / `issuerPersona`).

Signed metadata in front of the tail:

```json
{"app":"1sat_nft","issuerPersona":"studio","issuer":"<persona pubkey>","issuerOrigin":"<optional outpoint>"}
```

`app` is `1sat_nft` or `bsv21`. Name and traits that must be authoritative live in the signed inscription or the signed metadata, not in an unsigned URL.

A tag is not a proof. If the funding input outpoint is not known, a wallet MUST NOT append a signature. It MAY stamp custom instructions so a later step can sign. Custom instructions MAY include `issuerIdentity` (the wallet identity key), `issuerPersona`, `issuerGeneration`, `issuerName`, and `issuerOrigin`. Those fields are claims. They are linked only when the SIGMA address equals the BKDS child of that identity key at that persona path, and the VIN is bound.

[BRC-150](./../tokens/0150.md) is not modified. When the origin body is in the remittance BEEF, the tail is already in that script. The persona document is a different output. An unspent control output is a live check. It is not a BEEF.

Existing BSV-21 root [BRC-77](https://bsv.brc.dev) Sigma signing stays unless the output requests a Sigma persona. A requested persona skips the root signature and uses this BSM tail.

### Off-chain challenge

An API gateway MAY ask for a BSM signature by the persona key, never the root, over:

```
sigma-identity
<personaId>
<generation>
<publicKey>
<expiresAt>
<nonce>
```

Validity is 120 seconds, with 30 seconds of clock skew. The signature does not reveal the root and does not revoke anything. A gateway MUST also see an unspent control output for that generation. Revocation is the spend, not a message.

### Non-goals

- Replacing the root key or the BRC-169 handle.
- [BRC-52](https://bsv.brc.dev/wallet/0052.md) certificates, or a delegation that hands the child private key to another wallet. On this public path the child private key is equivalent to the root.
- A second identity protocol for "which wallet may sign." Portability is reconstruction from the identity key plus the persona id, and restore of the same root.
