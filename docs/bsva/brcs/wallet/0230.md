# BRC-230: Wallet Index Catalog Mirrors

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

This BRC defines index catalog mirrors: curated, public [BRC-24](./../overlays/0024.md) overlay indexes that a [BRC-100](./0100.md) wallet keeps locally, so applications can browse large collections and feeds without re-fetching the remote index on every screen.

Applications get one read-only surface: `listOutputs` on basket `p index read <packId>`, a [BRC-99](./0099.md) permission scheme modeled on [BRC-165](./../tokens/0165.md). Installing, syncing, budgeting and removing mirrors are wallet-internal; no new BRC-100 methods are defined.

Each returned row is a catalog projection of an overlay-admitted outpoint. Projections are not custody and cannot be spent. Held collectables stay in basket `1sat` ([BRC-147](./../tokens/0147.md)) with [BRC-150](./../tokens/0150.md) authenticity. This BRC does not change overlay admission or on-chain custody.

## Motivation

Overlay lookup answers "what exists on the network right now?", and its hosts are authoritative for live topical UTXO sets. A wallet-kept mirror adds:

1. Large catalogs: thousands of listings or feed cards without paging the overlay on every screen.
2. Faster verification: local walks, such as BRC-150 hydration against known origins, can beat cold overlay paging.
3. Offline browsing: the last synced pages stay visible while the wallet catches up.

Mirror rows are grade C convenience; they never stand in for held inventory or settlement state.

### When this BRC is not needed

An application that only wants faster navigation or offline UI for itself SHOULD cache overlay pages in its own storage and query BRC-24 for authoritative state. That needs no wallet support.

This BRC applies when a wallet vendor maintains public catalog mirrors as a wallet feature, or when several applications need a shared, user-approved read of the same mirror. [BRC-35](./../overlays/0035.md) KVStore holds wallet-local key/value tuples, not browsable catalog rows, and [BRC-165](./../tokens/0165.md) gates held inventory, not public catalogs.

## Terminology

| Term | Meaning |
|------|---------|
| Pack | One wallet-installed catalog mirror, identified by `packId`. |
| Manifest | JSON describing a pack's overlay source, scope, sync bounds, and optional curator signature. |
| Entry | One mirrored overlay row in a pack, keyed by `entryKey`. |
| Projection | A read-only `listOutputs` row returned under `p index read …`; not a spendable output. |
| Grade A | Chain custody. Mirrors never substitute for held UTXOs. |
| Grade C | Convenience: overlay index plus cached display metadata. |

The key words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, and MAY are used as in RFC 2119 and RFC 8174.

## Architecture

| Concern | Owner | Surface |
|---------|-------|---------|
| Live overlay state | BRC-24 hosts | `POST /lookup` from the application |
| App-local UI cache | Application | Application storage and freshness policy |
| Wallet catalog mirror | Wallet | Wallet-internal install, sync, remove |
| Cross-app read of a mirror | Wallet, with user grant | `listOutputs` on `p index read <packId>` |
| Custody, send, authenticity | Wallet basket `1sat` + BRC-150 | Unchanged ([BRC-165](./../tokens/0165.md)) |

Applications MUST NOT depend on controlling mirror install, sync, or removal, and MUST use live overlay lookup and held inventory for settlement or purchase decisions.

Pack installation is wallet-global: one mirror per `packId` per device. Read grants are per originator under scheme `index` ([BRC-116](./0116.md)); a grant for one `packId` MUST NOT grant read on any other. Removing a pack MUST NOT affect custody in `1sat`.

## Specification

### 1. Manifest

Curators publish a manifest at a stable HTTPS URL, and wallets fetch it during install. Applications MAY name manifest URLs they intend to read (§3.3) but MUST NOT supply manifest bytes to force an install.

```json
{
  "v": 1,
  "packId": "handcash.market.catalog",
  "name": "HandCash Market",
  "description": "Browse active 1Sat listings",
  "iconUrl": "https://market.handcash.io/icon.png",
  "curatorIdentityKey": "<33-byte-compressed-pubkey-hex>",
  "overlayBaseUrl": "https://market.handcash.io",
  "topic": "tm_1sat_market",
  "lookupService": "ls_1sat_market",
  "discovery": { "mode": "auto" },
  "scope": {
    "kind": "overlay-query",
    "query": { "mode": "active", "limit": 500 }
  },
  "budget": {
    "maxEntries": 5000,
    "maxBytes": 52428800,
    "maxBeefBytes": 1048576
  },
  "preview": {
    "beefB64": "<optional base64 BEEF for icon>"
  },
  "updatePolicy": {
    "mode": "onOpen",
    "intervalSeconds": 0
  },
  "signature": {
    "pubKeyHex": "<curatorIdentityKey>",
    "sigHex": "<DER ECDSA signature>"
  }
}
```

| Field | Requirement | Meaning |
|-------|-------------|---------|
| `v` | MUST | Schema version, `1`. |
| `packId` | MUST | 1–128 characters matching `[a-z0-9][a-z0-9.-]*`. |
| `name` | MUST | Pack title shown to the user, at most 80 UTF-8 code units. |
| `description` | SHOULD | Short explanation shown in the install prompt. |
| `iconUrl` | MAY | HTTPS icon, used when `preview.beefB64` is absent. |
| `curatorIdentityKey` | SHOULD | BRC-31 identity key of the publisher. |
| `discovery` | MAY | `mode` is `url` (use `overlayBaseUrl` and `hosts` only), `slap` (resolve hosts through SLAP, optionally via `slapTrackers`), or `auto` (curator hints, then SLAP). Default `auto`. |
| `overlayBaseUrl` | SHOULD; MUST when `discovery.mode` is `url` | HTTPS base URL of a BRC-24 host. |
| `topic` | MUST | BRC-87 topic manager name (`tm_*`). |
| `lookupService` | MUST | BRC-87 lookup service name (`ls_*`). |
| `scope` | MUST | §1.1. |
| `budget` | MUST | Hard caps, §1.2. |
| `preview` | MAY | Icon carried in [BRC-62](./../transactions/0062.md) BEEF. |
| `updatePolicy` | SHOULD | `mode` is `manual`, `onOpen`, or `interval`; `interval` requires `intervalSeconds` ≥ 300. |
| `signature` | MAY | ECDSA by `curatorIdentityKey` over SHA-256 of the manifest without `signature`, serialized as JSON with keys sorted and no whitespace. Wallets SHOULD verify it when present and MUST reject a manifest whose signature fails. |

Readers MUST ignore unknown manifest keys and MUST preserve them on round-trip. Wallets MUST reject a manifest whose `v` is not `1`.

#### 1.1 Scope kinds

| `scope.kind` | Meaning |
|--------------|---------|
| `overlay-query` | `scope.query` is passed unchanged to BRC-24 lookup on `lookupService`. |
| `collection` | `overlay-query` with `query.collectionId` set. |
| `feed` | Curator-defined query; `scope.query` MUST NOT change for a given `packId`. |

Wallets MUST NOT broaden `scope` beyond what the user approved at install. At read time an application MAY narrow results with tags (§4.1).

#### 1.2 Budget enforcement

When a sync would exceed `budget.maxEntries`, `budget.maxBytes`, or `budget.maxBeefBytes`, the wallet MUST stop, mark the pack `partial`, and keep existing entries. Pack budgets MUST NOT cause eviction of held outputs.

### 2. Wallet-internal storage

Mirror entries live outside custody, in a local database, a toolbox basket `index`, or an equivalent store. Applications see them only as projections (§4).

Each stored entry records:

| Field | Requirement |
|-------|-------------|
| `packId` | MUST |
| `entryKey` | MUST; stable key (§6) |
| `overlayOutpoint` | MUST; overlay-admitted outpoint as `txid.vout` |
| `tags` | SHOULD; include `pack:<packId>` and `entry:<entryKey>` |
| `customInstructions` | SHOULD; display claims (§2.1) |
| `beefB64` | MAY; row BEEF within `budget.maxBeefBytes` |
| `updatedAt` | SHOULD; Unix seconds of the last successful merge |

#### 2.1 Display metadata

`customInstructions` is UTF-8 JSON:

```json
{
  "packId": "handcash.market.catalog",
  "entryKey": "listing:abc123_0",
  "name": "Fetch coin",
  "imageUrl": "https://…",
  "origin": "abc123_0",
  "overlayOutpoint": "abc123_0",
  "beefB64": "<optional row BEEF>",
  "updatedAt": 1735689600
}
```

These are grade C display claims. Wallets MUST NOT treat `origin` or `overlayOutpoint` as held inventory without a separate custody import.

### 3. Permission scheme `index`

Scheme `index` gives applications read-only access to installed packs. It defines no install or sync values; those are wallet-internal (§5).

#### 3.1 Basket names

Per [BRC-99](./0099.md), the only form is `p index read <packId>`: read projections for one installed pack.

1. A bare `p index` MUST be rejected.
2. The scope token MUST be `read`.
3. `<packId>` MUST name an installed pack, or the request MUST fail with an error distinct from a permission denial.
4. After normalization, the `<packId>` segment contains only `[a-z0-9.-]`.

#### 3.2 Module detection

Applications MAY detect the scheme with a [BRC-98](./0098.md) probe:

```json
{
  "protocolID": [0, "p index probe"],
  "keyID": "index-module-probe",
  "counterparty": "self",
  "seekPermission": false
}
```

Success means the wallet routes scheme `index`. The probe grants nothing.

#### 3.3 Read grants

Payment grants and [BRC-165](./../tokens/0165.md) view grants do not cover scheme `index`. When an application calls `listOutputs` on `p index read <packId>`:

1. The wallet MUST route the request to the `index` permission module.
2. If the originator has no read grant for `<packId>`, the wallet MUST prompt or deny.
3. On approval, the wallet SHOULD store a durable grant for that originator and `packId`.
4. If the pack is not installed, the wallet MAY install and sync it before returning the first page. The prompt MUST then show the install scope and budgets.

Applications declare packs in the W3C manifest under `metanet.groupPermissions.basketAccess` ([BRC-116](./0116.md)):

```json
{
  "metanet": {
    "schemaVersion": 1,
    "groupPermissions": {
      "description": "Browse HandCash Market listings cached by your wallet",
      "basketAccess": [
        {
          "basket": "p index read handcash.market.catalog",
          "description": "Read the HandCash Market catalog mirror"
        }
      ]
    }
  }
}
```

An application MAY also list manifest URLs, which wallets MAY prefetch for grouped prompts. This is a hint, not an install API:

```json
{
  "metanet": {
    "indexPackManifests": [
      {
        "packId": "handcash.market.catalog",
        "manifestUrl": "https://market.handcash.io/v1/index-pack.json",
        "description": "HandCash Market active listings"
      }
    ]
  }
}
```

Readers MUST ignore unknown keys under `metanet`.

Scheme `index` does not authorize spending, sending, purchasing, or `createAction`; it gives no access to basket `1sat` or `p 1sat …`; and it does not let applications trigger sync or removal. A [BRC-123](./0123.md) registry entry is deferred, as for BRC-165 scheme `1sat`.

### 4. Application read API

#### 4.1 Request

Applications read with standard BRC-100 `listOutputs`:

```json
{
  "basket": "p index read handcash.market.catalog",
  "tags": ["collection:fetch"],
  "tagQueryMode": "all",
  "includeTags": true,
  "includeCustomInstructions": true,
  "limit": 50,
  "offset": 0
}
```

| Field | Rule |
|-------|------|
| `basket` | MUST be `p index read <packId>`. |
| `tags` | MAY narrow results. The wallet MUST return only entries in the pack, whatever `tagQueryMode` is. |
| `limit` / `offset` | Wallets MUST support `limit` from 1 to 500 and MAY clamp larger values to 500. Between syncs, pages MUST come from one stable order; `entryKey` ascending is RECOMMENDED. |

#### 4.2 Projection shape

Rows use the BRC-100 output shape but are catalog projections, not wallet outputs:

```json
{
  "outpoint": "abc123…_0",
  "basket": "index",
  "satoshis": 0,
  "tags": ["pack:handcash.market.catalog", "entry:listing:abc123_0"],
  "customInstructions": "{…}"
}
```

1. `outpoint` MUST equal the entry's `overlayOutpoint`. It names the catalog subject; it does not show the wallet holds that UTXO.
2. `satoshis` MUST be `0`.
3. `basket` SHOULD be the internal storage basket (`index`). Applications MUST NOT pass it to `createAction`.
4. Wallets MUST reject any attempt to spend, sign, or relinquish a projection.
5. `customInstructions` carries the display claims of §2.1. For owned items, BRC-150 on held `1sat` rows stays authoritative.

#### 4.3 Live reads

Applications that need live overlay state MUST query BRC-24 `/lookup` themselves or through their own backend. Wallets need not expose a live lookup. A wallet that offers one as a convenience MUST NOT merge its results into mirror rows outside a sync (§6).

### 5. Wallet-internal lifecycle

These operations belong to the wallet. Conformance MUST NOT require any BRC-100 method for them.

| Operation | Trigger | Behavior |
|-----------|---------|----------|
| Install | User accepts in wallet UI, or a first read grant for a pack with a known manifest (§3.3) | Fetch and validate the manifest, show scope and budgets, start the first sync |
| Sync | `updatePolicy`, wallet foreground, or a manual control | Merge from the overlay (§6) |
| Remove | User removes the pack | Delete the pack's entries; MUST NOT relinquish `1sat` custody |
| List | Wallet UI only | Show name, status, entry count, bytes used |

Applications conform by implementing §3–§4. Wallets that ship mirrors implement §1–§7.

### 6. Sync

1. Resolve overlay hosts according to `discovery.mode`, confirming each through `/listLookupServiceProviders`.
2. `POST /lookup` with `lookupService` and the approved `scope.query`.
3. For each admitted output, upsert an entry with `overlayOutpoint` set to its outpoint, merge display fields from the overlay context, and MAY fetch its BEEF within `budget.maxBeefBytes`. `entryKey` MUST be the same on every sync for the same outpoint; `listing:<txid>_<vout>` is RECOMMENDED.
4. A sync is full when it fetched every page of the scope within budget, and partial otherwise. After a full sync, entries the lookup no longer returned MUST be removed or marked `stale`. A partial sync MUST NOT remove or mark stale any entry it did not see.
5. On reaching a budget cap, stop and mark the pack `partial` (§1.2).

Wallets MAY fetch curator-published entry sets over [BRC-167 CHIRP](./../overlays/0167.md) or [BRC-26 UHRP](./../overlays/0026.md) instead of paging `/lookup`.

### 7. Activity

Install and sync SHOULD each emit an Activity row:

| Field | Value |
|-------|-------|
| `kind` | `event` |
| `method` | `index-install` or `index-sync` |
| `status` | `pending`, then `complete` or `failed` |
| `note` | Progress text |
| `item` | Optional preview from `preview` or `iconUrl` |

A failed row MUST set `failureReason`. A partial sync is `complete`, with the partial state in `note`.

### 8. Security considerations

1. Mirror rows are grade C: display and discovery only.
2. Purchases, sends, and authenticity MUST use held custody and BRC-150.
3. Wallets MUST NOT run scripts or spend UTXOs because a mirror row exists.
4. Wallets MUST NOT install a manifest the user has not approved.
5. Cached BEEF is a preview and SPV hint; it MUST NOT override live overlay state for settlement.
6. A read grant MUST NOT imply write, sync, or install rights.

| Field | Value |
|-------|-------|
| `packId` | `handcash.market.catalog` |
| `topic` | `tm_1sat_market` |
| `lookupService` | `ls_1sat_market` |
| `scope.kind` | `overlay-query` |

A wallet may expose extra BRC-100 methods for debugging or migration, such as `installIndexExpansion`, `listIndexExpansions`, `removeIndexExpansion`, `syncIndexExpansion`, `listIndexExpansionEntries`, and `overlayLookup`. Conformance MUST NOT require them.
