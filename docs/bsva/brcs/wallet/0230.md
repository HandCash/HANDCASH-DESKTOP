# BRC-230: Wallet Index Catalog Mirrors

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (revision — wallet-internal lifecycle, read-only app surface)

## Abstract

This BRC defines **Index Catalog Mirrors**: curated, public [BRC-24](./../overlays/0024.md) overlay
indexes that a [BRC-100](./0100.md) wallet **may retain locally** so applications can browse
large collections, feeds, and other grade-**C** discovery catalogs **without re-fetching the full
remote index on every navigation**.

The normative **application-facing** surface is a single read-only permission scheme under
[BRC-99](./0099.md): `listOutputs` on basket **`p index read <packId>`**, modeled after
[BRC-165](./../tokens/0165.md) P1Sat view routing. **Installation, synchronization, removal,
budget enforcement, and eviction remain wallet-internal operations** — applications do not
control pack lifecycle through new BRC-100 methods.

Each returned row is a **catalog projection** referencing an overlay-admitted UTXO outpoint.
Projections are **not custody** and MUST NOT be spendable. Held collectables remain in basket
`1sat` ([BRC-147](./../tokens/0147.md)) with [BRC-150](./../tokens/0150.md) authenticity.

This document composes BRC-22, BRC-24, [BRC-87](./../overlays/0087.md),
[BRC-88](./../overlays/0088.md), BRC-99, BRC-100, BRC-116, [BRC-164](./0164.md), and
optional [BRC-167 CHIRP](./../overlays/0167.md) transport. It does not redefine overlay
admission rules or on-chain custody.

## Motivation

Overlay lookup ([BRC-24](./../overlays/0024.md)) answers “what exists on the network right
now?” Remote hosts are authoritative for **live** topical UTXO sets. Product experiences
also want:

1. **Large catalogs** — thousands of listings or feed cards where paging the overlay on
   every screen is slow or expensive.
2. **Wallet-assisted verification** — when the wallet already holds a bounded mirror of
   a collection index, local walks (e.g. BRC-150 hydration against known origins) can be
   faster than cold overlay paging alone.
3. **Offline-friendly browsing** — show the last synced page set while the wallet catches
   up in the background.
4. **Clear trust boundaries** — mirror rows are **grade C** convenience only; they MUST NOT
   substitute for held inventory or settlement state.

### When this BRC is not required

If the requirement is **only** faster in-app navigation or offline UI for a single
application, the application SHOULD cache overlay pages in its own storage (IndexedDB,
SQLite, CDN, service worker, etc.) and query BRC-24 directly for authoritative state.
**No wallet or BRC-100 extension is required.**

This BRC applies when:

- A **wallet vendor** chooses to install and maintain public catalog mirrors as a
  wallet-native convenience (Settings, Activity, background sync), **and/or**
- Multiple applications need a **shared, user-approved read surface** to the same
  wallet-maintained mirror without each app re-downloading the full index.

[BRC-35](./../overlays/0035.md) local KVStore solves wallet-local key/value tuples, not
“mirror this overlay lookup into browsable catalog rows.” [BRC-165](./../tokens/0165.md)
P1Sat permissions gate **held** inventory, not public catalog mirrors.

## Terminology

| Term | Meaning |
|------|---------|
| **Pack** | One wallet-installed catalog mirror identified by `packId`. |
| **Manifest** | JSON document describing overlay source, scope, sync bounds, and optional curator signature. |
| **Entry** | One mirrored overlay row keyed by `entryKey` inside a pack. |
| **Projection** | A read-only `listOutputs` row returned under `p index read …`; not a spendable wallet output. |
| **Grade A** | Chain custody — unchanged; mirrors never substitute for held UTXOs. |
| **Grade C** | Convenience oracle — overlay index + cached display metadata. |

## Normative language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**, and **MAY**
are normative (RFC 2119 / RFC 8174).

## Architecture

### Separation of concerns

| Concern | Owner | Normative surface |
|---------|-------|-------------------|
| Live overlay state | BRC-24 hosts | Application `POST /lookup` (or wallet-hosted proxy — out of scope) |
| App-local UI cache | Application | Application storage + freshness policy |
| Wallet catalog mirror | Wallet vendor | Wallet-internal install / sync / remove |
| Cross-app read of a wallet mirror | Wallet + user grant | `listOutputs` basket `p index read <packId>` |
| Custody, send, authenticity | Wallet `1sat` + BRC-150 | Unchanged ([BRC-165](./../tokens/0165.md)) |

Applications MUST NOT depend on controlling mirror install, sync, or removal. When an
application needs authoritative settlement or purchase state, it MUST use live overlay
lookup and held inventory — not the mirror alone.

### Pack state vs permissions

- **Pack installation** is **wallet-global** (one mirror per `packId` on the device).
- **Read grants** are **per originator** under scheme `index` ([BRC-116](./0116.md)).
- Granting `p index read <packId>` to an application MUST NOT grant read on other packs.
- Removing a pack is a wallet operation; it MUST revoke no held custody in `1sat`.

## Specification

### 1. Manifest

Curators publish a manifest at a stable HTTPS URL. Wallets fetch manifests during
wallet-internal install. Applications MAY declare manifest URLs they intend to read
(see §3.2) but MUST NOT supply manifest bytes to force installation.

```json
{
  "v": 1,
  "packId": "handcash.market.catalog",
  "name": "HandCash Market",
  "description": "Browse active 1Sat listings",
  "iconUrl": "https://market.handcash.io/icon.png",
  "curatorIdentityKey": "<33-byte-compressed-pubkey-hex>",
  "overlayBaseUrl": "https://market.handcash.io",
  "topic": "tm_1sat_market",
  "lookupService": "ls_1sat_market",
  "discovery": { "mode": "auto" },
  "scope": {
    "kind": "overlay-query",
    "query": { "mode": "active", "limit": 500 }
  },
  "budget": {
    "maxEntries": 5000,
    "maxBytes": 52428800,
    "maxBeefBytes": 1048576
  },
  "preview": {
    "beefB64": "<optional base64 BEEF for icon>"
  },
  "updatePolicy": {
    "mode": "onOpen",
    "intervalSeconds": 0
  },
  "signature": {
    "pubKeyHex": "<curatorIdentityKey>",
    "sigHex": "<ECDSA over canonical manifest bytes>"
  }
}
```

| Field | Requirement | Meaning |
|-------|-------------|---------|
| `v` | MUST | Manifest schema version. This BRC defines `1`. |
| `packId` | MUST | Stable UTF-8 id, 1–128 chars, `[a-z0-9][a-z0-9.-]*`. |
| `name` | MUST | User-facing pack title (≤ 80 UTF-8 code units). |
| `description` | SHOULD | Short explanation shown in wallet install UI. |
| `iconUrl` | MAY | HTTPS preview when `preview.beefB64` absent. |
| `curatorIdentityKey` | SHOULD | BRC-31 identity key of the pack publisher. |
| `overlayBaseUrl` | SHOULD | HTTPS curator hint for BRC-24 `/lookup`. Required when `discovery.mode` is `url`. |
| `discovery` | MAY | Host resolution: `mode` (`auto` \| `slap` \| `url`), optional `hosts`, `slapTrackers`. |
| `topic` | MUST | BRC-87 topic manager name (`tm_*`). |
| `lookupService` | MUST | BRC-87 lookup service name (`ls_*`). |
| `scope` | MUST | See §1.1. |
| `budget` | MUST | Hard caps enforced by the wallet. |
| `preview` | MAY | Optional BEEF-carried icon ([BRC-62](./../transactions/0062.md)). |
| `updatePolicy` | SHOULD | `manual`, `onOpen`, or `interval` with `intervalSeconds ≥ 300`. |
| `signature` | MAY | Curator signature over canonical JSON (keys sorted, no whitespace). Wallets SHOULD verify when present. |

Unknown manifest keys MUST be preserved on round-trip and ignored by readers that do not
understand them. Wallets MUST reject manifests with `v !== 1`.

#### 1.1 Scope kinds

| `scope.kind` | Meaning |
|--------------|---------|
| `overlay-query` | Pass `scope.query` verbatim to BRC-24 lookup (service = manifest `lookupService`). |
| `collection` | Equivalent to `overlay-query` with `query.collectionId` set. |
| `feed` | Curator-defined query template; `scope.query` MUST be stable for the pack id. |

Wallets MUST NOT broaden `scope` beyond what the user approved during wallet-internal
install. Applications MAY request a **narrower** tag filter at read time only if the
filter is a sub-set of the approved scope.

#### 1.2 Budget enforcement

When `budget.maxEntries`, `budget.maxBytes`, or `budget.maxBeefBytes` would be exceeded,
sync MUST stop cleanly, mark the pack `partial`, and leave prior entries intact. Wallets
MUST NOT silently evict held custody outputs to satisfy pack budgets.

### 2. Wallet-internal storage

Mirror entries live **outside custody**. Wallets MAY persist them in a local database,
toolbox basket `index`, or equivalent internal profile. This storage is **not** exposed
to applications except through catalog projections (§4).

Each stored entry MUST record at minimum:

| Field | Requirement |
|-------|-------------|
| `packId` | MUST |
| `entryKey` | MUST — stable mirror key (see §6) |
| `overlayOutpoint` | MUST — outpoint string from overlay admission (`txid.vout`) |
| `tags` | SHOULD — include `pack:<packId>` and `entry:<entryKey>` |
| `customInstructions` | SHOULD — UTF-8 JSON display claims (§2.1) |
| `beefB64` | MAY — optional row BEEF within `budget.maxBeefBytes` |
| `updatedAt` | SHOULD — unix seconds of last successful merge |

#### 2.1 Display metadata (`customInstructions`)

```json
{
  "packId": "handcash.market.catalog",
  "entryKey": "listing:abc123_0",
  "name": "Fetch coin",
  "imageUrl": "https://…",
  "origin": "abc123_0",
  "overlayOutpoint": "abc123_0",
  "beefB64": "<optional row BEEF>",
  "updatedAt": 1735689600
}
```

Fields are **display claims** (grade C). Wallets MUST NOT treat `origin` or
`overlayOutpoint` as proven held inventory without a separate custody import.

### 3. Permission scheme (BRC-99)

Scheme id: **`index`**

This scheme exposes **read-only catalog view** to applications. It does **not** define
install or sync wire values — those operations are wallet-internal (§5).

#### 3.1 Basket namespace

Per [BRC-99](./0099.md):

| Form | Meaning |
|------|---------|
| `p index read <packId>` | Read cached catalog projections for one installed pack. |

Rules:

1. Bare `p index` (no scope token) MUST be rejected.
2. Scope token MUST be exactly `read`. Tokens `install` and `sync` MUST NOT appear in
   application `listOutputs` basket names.
3. `<packId>` MUST match an installed pack id. Unknown or uninstalled packs MUST fail
   closed with a distinct error.
4. Basket names use only `[a-z0-9 .-]` in the pack id segment after normalization.

#### 3.2 Module detection

Applications MAY detect scheme support with a [BRC-98](./0098.md) probe:

```json
{
  "protocolID": [0, "p index probe"],
  "keyID": "index-module-probe",
  "counterparty": "self",
  "seekPermission": false
}
```

Success indicates the wallet routes scheme `index`. The probe grants no read rights.

#### 3.3 View grants ([BRC-116](./0116.md))

Read access is **not** covered by payment / auto-pay grants or [BRC-165](./../tokens/0165.md)
P1Sat view grants.

When an application calls `listOutputs` with basket `p index read <packId>`:

1. The wallet MUST route the request to the `index` permission module.
2. If the originator lacks a read grant for `<packId>`, the wallet MUST prompt (or deny).
3. On approval, the wallet SHOULD persist a durable read grant for that originator and
   `packId`.
4. If the pack is not yet installed, the wallet MAY begin wallet-internal install +
   initial sync before returning the first page (user MUST see install scope in the
   combined prompt).

Applications declare intended packs in the W3C manifest under `metanet.groupPermissions`
using **`basketAccess`** ([BRC-116](./0116.md)) — not a custom `protocol: "index"` object:

```json
{
  "metanet": {
    "schemaVersion": 1,
    "groupPermissions": {
      "description": "Browse HandCash Market listings cached by your wallet",
      "basketAccess": [
        {
          "basket": "p index read handcash.market.catalog",
          "description": "Read the HandCash Market catalog mirror"
        }
      ]
    }
  }
}
```

Optional curator hint for wallet install UI (informative to wallets; not an install API):

```json
{
  "metanet": {
    "indexPackManifests": [
      {
        "packId": "handcash.market.catalog",
        "manifestUrl": "https://market.handcash.io/v1/index-pack.json",
        "description": "HandCash Market active listings"
      }
    ]
  }
}
```

Wallets MAY use `indexPackManifests` to prefetch manifest metadata for grouped prompts.
Unknown keys under `metanet` MUST be ignored by readers that do not implement them.

#### 3.4 Out of scope for scheme `index`

- Spend, send, purchase, or `createAction` authorization
- Implied access to basket `1sat` or `p 1sat …`
- Application-triggered sync or removal

[BRC-123](./0123.md) registry listing for scheme `index` is deferred (same posture as
[BRC-165](./../tokens/0165.md) scheme `1sat`).

### 4. Application read API (`listOutputs`)

The normative cross-application API is standard BRC-100 **`listOutputs`**.

#### 4.1 Request

```json
{
  "basket": "p index read handcash.market.catalog",
  "tags": ["collection:fetch"],
  "tagQueryMode": "all",
  "includeTags": true,
  "includeCustomInstructions": true,
  "limit": 50,
  "offset": 0
}
```

| Field | Rule |
|-------|------|
| `basket` | MUST be `p index read <packId>`. |
| `tags` | MAY narrow results; MUST NOT widen beyond installed scope. |
| `limit` / `offset` | Pagination; wallet MUST support `limit` 1–500. |

#### 4.2 Catalog projection shape

Each returned object mirrors the BRC-100 output list shape for interoperability, but
normatively represents a **catalog projection**, not a spendable wallet output:

```json
{
  "outpoint": "abc123…_0",
  "basket": "index",
  "satoshis": 0,
  "tags": ["pack:handcash.market.catalog", "entry:listing:abc123_0"],
  "customInstructions": "{…}"
}
```

Rules:

1. **`outpoint`** MUST equal the overlay-admitted outpoint (`overlayOutpoint`) for the
   row. It identifies the catalog subject; it is **not** proof the wallet holds that UTXO.
2. **`satoshis`** MUST be `0`. Projections MUST NOT carry spendable value.
3. **`basket`** in the response SHOULD be the internal storage basket name (`index`) for
   debugging; applications MUST NOT pass this basket to `createAction`.
4. Wallets MUST reject any attempt to spend, sign, or relinquish catalog projections.
5. **`customInstructions`** carries grade-C display JSON (§2.1). It does not grant
   authenticity; [BRC-150](./../tokens/0150.md) on held `1sat` rows remains authoritative
   for owned items.

This resolves the custody vs cache typing issue: applications receive a **stable
listOutputs projection** referencing real overlay outpoints, explicitly labeled
non-spendable, rather than pretending arbitrary cache cards are tracked wallet UTXOs.

#### 4.3 Live authoritative reads

Applications needing **live** overlay state MUST query BRC-24 `/lookup` directly (or
through their own backend). This BRC does not require wallets to expose a live lookup
method. Wallets MAY offer a non-normative proxy for convenience; live results MUST NOT
be silently merged into mirror rows without a wallet-internal sync pass.

### 5. Wallet-internal lifecycle

The following operations are **wallet-owned**. They MUST NOT be required BRC-100 vendor
methods for conformance.

| Operation | Trigger | Behavior |
|-----------|---------|----------|
| **Install** | User accepts install in wallet UI, or first read grant for an undeclared pack with curator manifest | Fetch manifest, validate, show scope + budgets, begin initial sync |
| **Sync** | `updatePolicy`, wallet foreground, manual Settings control | Incremental overlay merge (§6) |
| **Remove** | Settings → remove pack | Delete mirror rows for `packId`; MUST NOT relinquish `1sat` custody |
| **List installed** | Wallet UI only | Show pack name, status, entry counts, bytes used |

Wallets SHOULD emit Activity rows for install/sync (§7).

Conformance for **applications**: implement §3–§4 only.

Conformance for **wallets** that ship catalog mirrors: implement §1–§2, §5–§7, and §3–§4.

### 6. Sync algorithm

Wallet-internal sync outline:

1. Resolve overlay hosts (curator hints → SLAP → `/listLookupServiceProviders` verify).
2. POST BRC-24 `/lookup` with manifest `lookupService` and approved `scope.query`.
3. For each admitted output:
   - Compute stable `entryKey` (RECOMMENDED: `listing:<txid>_<vout>` or overlay context id).
   - Upsert entry with `overlayOutpoint = outpoint`.
   - Merge `customInstructions` display fields from overlay context.
   - Optionally fetch row BEEF within `budget.maxBeefBytes`.
4. **Incremental merge:** entries present locally but absent from the latest successful
   lookup page set for the approved scope SHOULD be marked `stale` or removed on full
   sync; partial syncs MUST NOT delete unseen rows unless `force: true` wallet policy.
5. **Removals:** when an outpoint drops out of overlay admission, remove or mark stale
   the matching `entryKey`.
6. Stop at budget caps; set pack status `partial` when truncated.
7. Large manifests MAY use [BRC-167 CHIRP](./../overlays/0167.md) / [BRC-26 UHRP](./../overlays/0026.md)
   when the curator publishes blob roots.

### 7. Activity contract (wallet UI)

Install and sync SHOULD emit Activity rows:

| Field | Value |
|-------|-------|
| `kind` | `event` |
| `method` | `index-install` or `index-sync` |
| `status` | `pending` → `complete` \| `failed` |
| `note` | Human-readable progress |
| `item` | Optional preview from manifest `preview` or `iconUrl` |

Failures MUST set `failureReason`. Partial sync SHOULD still mark `complete` with a note.

### 8. Trust and security

1. Mirror rows are **grade C** — display and discovery only.
2. Purchases, sends, and authenticity MUST use held custody + BRC-150 as today.
3. Wallets MUST NOT execute scripts or spend UTXOs because a mirror row exists.
4. Manifests from untrusted origins MUST fail closed unless the user approves install.
5. Cached BEEF is for preview/SPV hints; it MUST NOT override live overlay state for
   settlement decisions.
6. Read grants MUST NOT imply write, sync, or install rights for applications.

### 9. Reference profile — 1Sat Market catalog

| Field | Value |
|-------|-------|
| `packId` | `handcash.market.catalog` |
| `topic` | `tm_1sat_market` |
| `lookupService` | `ls_1sat_market` |
| `scope.kind` | `overlay-query` |
| HandCash settlement | Unchanged — market BRC-100 methods remain host-gated |

This profile is **informative**; the normative pack format is §1.

## Informative appendix: vendor extensions

Some wallets (including HandCash Desktop/Mobile) may expose additional **non-normative**
BRC-100 vendor methods for debugging, migration, or legacy clients:

- `installIndexExpansion`, `listIndexExpansions`, `removeIndexExpansion`,
  `syncIndexExpansion`, `listIndexExpansionEntries`, `overlayLookup`

These methods duplicate wallet-internal lifecycle or live lookup helpers. They MUST NOT
be required for BRC-230 conformance. New applications SHOULD use `listOutputs` (§4) for
reads and BRC-24 for live authoritative state.
