# BRC-249: Vault Account Holding Across Devices

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

A [BRC-208](./0208.md) vault master opens many accounts, and the same backup can be restored on several devices. Two installs that open one account are two spenders of one key: each picks coins from its own copy of the account's state, and they double-spend each other. This BRC keeps every account on exactly one install at a time without putting the network on the spend path.

Each account is **held** by one install. Holding is local state, and a wallet refuses to open or sign for an account it does not hold. Other installs learn who holds an account from a small **holder record** signed by the account's own root and stored beside the account's history backup. The record changes only on three explicit events: an install reserves a new account, takes an account, or releases one. Its sequence number only grows, so a host can delay a change but cannot forge or roll one back.

## Motivation

BRC-208 lets one backup recover every account, but says nothing about two devices using one vault at once. Three problems follow.

1. **Shared accounts double-spend.** Two installs that both open account 0 each build transactions from their own view of its outputs. One install's spend is invisible to the other until a chain refresh, and outputs that only one install's local state knows about (for example, BRC-29 change) never become visible to the other. A spend lease checked before each payment would prevent the conflict, but it costs a round trip on every payment and fails when the host is unreachable.
2. **Allocation races.** BRC-208 allocates the next account as one more than the highest index ever allocated. Two devices that each create an account at the same time pick the same index, which is the same key.
3. **Moving between devices.** A user who wants their spending wallet on a phone and their savings on a laptop needs to hand an account from one device to the other, with its history, and have the first device stop.

Holding accounts per device solves all three. Devices that share a vault use different accounts, so they never share a coin. Reserving an index is a conditional create, so two devices cannot reserve the same one. Moving an account is a release on one device followed by a take on the other.

## Terminology

| Term | Meaning |
|---|---|
| Install | One wallet installation with its own local state and a random **device id**. |
| Held here | This install may open the account, build its state and sign for it. |
| Held elsewhere | Another install holds the account, or released it and nobody has taken it yet. |
| Holder record | The signed JSON object below, one per account. |
| History host | The host that stores the account's history backup (for example, a BRC-38 export of its local state encrypted under BRC-39). |

## Specification

### Holder record

```json
{
  "v": 1,
  "identityKey": "<account identity key, compressed hex, lower case>",
  "deviceId": "<install's device id, 1–128 characters>",
  "state": "held" | "released",
  "seq": <integer ≥ 1>,
  "at": <milliseconds since the Unix epoch>,
  "signature": "<hex>"
}
```

`signature` is a 64-byte compact ECDSA signature (`r ‖ s`, hex) by the account root over the SHA-256 of the UTF-8 preimage:

```
account-holder
v1
<identityKey>
<deviceId>
<state>
<seq>
<at>
```

Lines are joined with a single `\n` and there is no trailing newline. Nonces are deterministic per RFC 6979. `at` is informational only; ordering comes from `seq`.

A reader MUST reject a record whose `identityKey` is not the account it asked for, whose `seq` is not a positive safe integer, or whose signature does not verify. A rejected record counts as an unreachable host, not as an absent record.

The device id SHOULD be random and SHOULD NOT be derived from any key or hardware identifier. It is visible to the history host.

### Storage

The holder record lives on the account's history host, beside its history backup, at a path the host scopes to the account identity key (HandCash uses `/v1/wallets/<identityKey>/holder.json`). The host:

1. MUST accept reads and writes only from requests authenticated as that identity key (for example, a request signed by the account root under BRC-103 or BRC-104).
2. MUST return an `ETag` with every read.
3. MUST honour `If-None-Match: *` on write (create only when absent) and `If-Match: <etag>` (replace only that version), and MUST answer `412` when the condition fails.
4. SHOULD store records only when they are signed records of this form, and MAY cap their size (4 KB is ample).

A host that does not support holder records answers `404` or `405` on the path. A wallet MUST NOT trust the host for anything beyond availability; the signature and `seq` carry the meaning.

### Local holding

For every account it lists, a wallet keeps `held here` or `held elsewhere`, plus the highest `seq` it has acted on (`0` when no record has been seen). The rules below are the only ways that state changes.

### Spending

A wallet:

1. MUST NOT open, preload, sign for or spend from an account it does not hold. BRC-100 requests while such an account would be active MUST be refused.
2. MUST decide holding from local state alone on the spend path. It MUST NOT make a network request to authorize a payment.
3. MUST stop spending an account the moment a check finds it held elsewhere, and SHOULD leave it for an account it holds.

### Checking

A wallet SHOULD check the accounts it lists after unlock, before opening an account, and periodically for the active account (HandCash checks every five minutes). For each account it reads the record and:

1. **Host unreachable or unsupported:** keeps its local holding.
2. **No record:** if it holds the account, publishes `held` with `seq` one more than its local `seq`, create-only. Otherwise keeps its local holding.
3. **Record older than local** (`record.seq < local.seq`): its own newer write is missing. If it holds the account it republishes `held` with `seq = local.seq + 1`, conditioned on the record's ETag; otherwise it keeps its local holding.
4. **Otherwise:** adopts the record. `held` with this install's device id means held here; anything else means held elsewhere.

A conditional write that fails with `412` means another install wrote first. The wallet re-reads and decides again.

### Reserving a new account

This replaces BRC-208's allocation rule for wallets that implement this BRC. Starting from the next index this install would allocate:

1. Read the candidate's record. If one exists, the index is in use: list it as held elsewhere (as the record says) and try the next index.
2. Check the candidate for use as BRC-208 discovery does (history backup, waiting messages). If used, list it as held elsewhere and try the next index. If any source cannot answer, stop.
3. Write `held`, `seq` 1, create-only. On success the account is held here. On `412`, try the same index again from step 1.
4. If the history host cannot be reached, stop. The wallet MUST NOT create an account it could not reserve.

A history host without holder records cannot arbitrate. A wallet MAY then allocate locally only when every account it lists is held here; otherwise it MUST refuse.

### Releasing

To move an account to another install, the holding install:

1. Refuses new spends on the account and waits for spends in progress to finish.
2. Uploads the account's history backup and any other state another install needs to spend it (for example, recipes for outputs whose keys need more than the account root). If any of this fails, it stops; the account stays held here.
3. Writes `released` with `seq` one more than the higher of its local `seq` and the record's, conditioned on the record's ETag (create-only when absent). If the record names another holder at an equal or higher `seq`, it adopts that record instead and stops.
4. On success, marks the account held elsewhere. If anything changed during the upload, it uploads again.

### Taking

To hold an account another install held, a wallet reads its record:

1. **`released`, or `held` by this install:** writes `held` with `seq + 1` conditioned on the ETag (or adopts its own record). No confirmation is needed.
2. **`held` by another install, or no record on an account in use:** the wallet MUST ask the user first. It MUST say that the other install stops spending the account only when it next checks, so it should be offline, lost or wiped. On confirmation it writes `held` with `seq + 1`, conditioned on the ETag, or create-only when absent.
3. **Host unreachable or unsupported:** the take fails.

After taking an account, the wallet MUST bring the history backup into local state before it spends. That backup was uploaded by the releasing install and is newer than any copy this install kept from before. The merge MUST NOT be deferred for a waiting payment.

### Restoring onto a new device

Restoring a backup onto a device asks how the new install relates to the old one:

- **Replace:** the new install takes over. It marks every account it opens as held here and, on its first check, publishes `held` over whatever each record says (`seq = max(record.seq, local.seq) + 1`). The old install gives the accounts up at its next check.
- **Keep both:** the old install keeps its accounts. The new install MUST complete BRC-208 discovery first; if any source cannot answer, the restore fails. It then lists every discovered account as held elsewhere, checks them, and reserves a new account for itself.

A wallet SHOULD default to Replace, which matches a restore after a lost device.

### Upgrading

Accounts in use before a wallet implements this BRC have no record. Each install that already held an account publishes it create-only on its first check. When two installs of one vault upgrade, the first to publish keeps the account; the other adopts the record and gives it up. A user who wants both devices to keep spending moves accounts until each install holds different ones.

## Security considerations

- **The host cannot forge or roll back.** Only the account root can sign a record, and readers ignore a record older than the one they last acted on. A host that wants to cause harm can only withhold a change. A withheld take leaves the old install spending until its next successful check; a withheld release blocks a move without moving anything.
- **A forced take of a live install opens a window.** Until the old install checks, both installs may spend. The conflicting transactions double-spend each other, so miners accept at most one of them. Both installs belong to the same vault owner, nothing is stolen, and the losing install refreshes from the chain. That is why a forced take requires confirmation and wording that the other device should be offline.
- **Holding is not authority.** Anyone who holds the vault master can derive and spend every account regardless of any record. Holding coordinates honest installs of one owner; it does not protect against a stolen backup.
- **Privacy.** The history host learns the account identity keys it stores, which it already knew from the history backups, and the device ids that hold them, which reveals how many installs share a vault. Device ids SHOULD be random to avoid linking installs across vaults.
- **Fail closed.** Every path that cannot reach the host or verify a record keeps the more restrictive state: reserving refuses, a take fails, a release keeps the account held here, and an upgrading install that loses the create gives the account up.

## Rationale

- **Why not a spend lease?** A lease checked before each payment puts a network round trip on every spend and stops payments whenever the host is unreachable. HandCash shipped one and removed it after it cost about 1.7 seconds per payment. Holding moves the coordination to rare, explicit events, and payments stay local.
- **Why per account and not per vault?** Accounts have separate keys and separate coins, so two installs holding different accounts never compete for an output. Holding the whole vault on one device would make a phone and a laptop on one backup impossible.
- **Why the history host?** A take has to be ordered after the releasing install's history upload. Keeping the record beside that upload, under the same authentication, means one host orders both. Each account's history is already scoped to its own identity key there.
- **Why a sequence number and not timestamps?** Device clocks disagree, and a host could replay an old record with a plausible time. A counter that only grows, checked by each reader against what it last acted on, needs neither synchronized clocks nor a trusted host.

## Non-goals

- Two installs spending one account at the same time. That needs shared state for every output, not a holder.
- Syncing an account's history continuously between devices. History moves with the account, at release and take.
- Choosing which account a payment uses. Moving value between accounts is an ordinary payment.

## Implementations

- HandCash Desktop and Mobile hold BRC-208 accounts per install. The wallet menu lists accounts held elsewhere as "On another device", with Move here and Move to another device. A restore asks whether to replace the old device or keep both. BRC-CLOUD stores holder records with create-only and ETag-conditional writes beside each account's BRC-39 backup.
