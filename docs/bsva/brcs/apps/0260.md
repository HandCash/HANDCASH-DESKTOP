# BRC-260: Chart Apps — Signed State-Chart Apps Run by the Wallet

- **Status:** Draft. HandCash's draft with a proposed number (260). Not merged into the BSVA BRCs repository and not a published standard.
- **Authors:** HandCash
- **Category:** Wallet
- **Format tag:** `chart-app/1`

## Abstract

A chart app is a small JSON state chart that a wallet verifies and renders itself. The chart lists its states, the input and display blocks each state shows, and every effect it may cause. Effects are the only way a chart can reach money, identity, the network or the user's message boxes, and each effect that moves money, shares identity, or clears or blocks mail waits for the user's approval. A chart is hashed in canonical JSON and signed by its author's identity key, so it can be shared by hash and checked before it runs. The format names no chain: payment, request and item effects name their coin and network, and each wallet declares what it supports.

## Motivation

Some wallet experiences are small, isolated and specialised: ask a friend for an amount, keep a tip jar, split a bill, tidy a message box. Building each one as a website means hosting it, trusting its script with a connected wallet, and asking the user to judge an origin. Building each one into the wallet means a wallet release per idea.

Chart apps sit between the two. The whole app is a few kilobytes of declarative data. Before it runs, the wallet can show every step it can take and every effect it can cause, and it draws every screen with its own controls, so an app cannot dress up an approval or read anything it did not declare.

Chart apps are **not** a replacement for websites or general apps. They have no script, no layout of their own and no free network access, on purpose. They suit short flows with a handful of states and a few effects. Anything larger belongs on the web, connected to the wallet over BRC-100.

## Specification

The key words MUST, MUST NOT, SHOULD and MAY are as in RFC 2119.

### 1. Chart

A chart is a JSON object with exactly these members. A wallet MUST refuse a chart with any other member, anywhere in the document, at any depth that this section defines.

| Member | Type | Rule |
|---|---|---|
| `format` | string | `"chart-app/1"` |
| `id` | string | `^[a-z][a-z0-9-]{1,39}$`, stable across versions |
| `name` | string | 1 to 40 characters |
| `summary` | string | 1 to 140 characters, what the app does |
| `version` | string | `major.minor.patch` |
| `author` | object | `{ identityKey, name }`: compressed secp256k1 public key in lowercase hex, and a display name of 1 to 40 characters |
| `initial` | string | name of a state |
| `fields` | object | field name → field (§2) |
| `effects` | object | effect id → effect (§5) |
| `states` | object | state name → state (§4) |
| `signature` | string | DER ECDSA signature in hex (§7) |

Names of fields, effects and states match `^[a-z][a-zA-Z0-9]{0,31}$`. Numbers anywhere in a chart MUST be integers. The canonical JSON of a chart (§6) MUST NOT exceed 32,768 bytes.

### 2. Fields

Fields hold the chart's values. Only the wallet writes them: from the user's input in a block that shows the field, from a transition's literal `assign`, or from an effect's result.

| Type | Holds | Written by |
|---|---|---|
| `amount` | positive integer in the base unit of its `coin` (required member) | amount input, `assign` |
| `text` | string up to `maxLength` (1 to 500, default 140) | text input, `assign` |
| `friend` / `friends` | one / several contacts the user picked | friend picker |
| `item` | one item the user holds | item picker |
| `messages` | messages listed from a box | `listMessages` |
| `senders` | blocked senders | `listMessages` |
| `selection` | ids of listed messages the user ticked | list block |
| `message` / `sender` | one listed message / sender the user opened | list block |
| `signature` | identity key, signature and signed text | `signMessage` |
| `fetched` | status and up to 4,000 characters of body | `fetch` |

### 3. Blocks

A state's `view` is an ordered list drawn from this fixed set. A wallet MUST refuse any other block.

| Block | Members |
|---|---|
| `heading`, `text` | `text` |
| `amountInput` | `field` (amount), `label` |
| `textInput` | `field` (text), `label`, optional `placeholder` |
| `friendPicker` | `field` (friend or friends), `label` |
| `itemPicker` | `field` (item), `label` |
| `list` | `field` (messages or senders), optional `label`, `select` (selection), `open` `{ event, field }`, `empty` |
| `primaryButton`, `secondaryButton` | `label`, `event` |

Text may hold placeholders `{field}` or `{field.key}`. Keys by type: `friends`, `messages`, `senders`, `selection`: `count`; `message`: `sender`, `box`, `kind`, `time`, `text`; `signature`: `signature`, `identityKey`; `fetched`: `status`, `text`. Any other placeholder makes the chart invalid. The wallet formats each value itself.

### 4. States and transitions

Each state is exactly one of:

- **View state:** `view` and optional `on`, mapping event names to a target state name or `{ target, requires?, assign? }`. `requires` lists fields that MUST hold a value before the transition is taken. `assign` writes literal integers to amount fields or strings to text fields.
- **Effect state:** `effect` (a declared effect id), `onDone` and `onError` (state names), and `onDecline` (a state name) exactly when the effect needs approval (§8).
- **Final state:** `final: true` and a `view`, with no `on`.

Event names match `^[A-Z][A-Z0-9_]{0,31}$`. `SET`, `TOGGLE`, `APPROVE` and `DECLINE` are reserved for the wallet. Every event a block sends MUST have a transition in that state, and every transition MUST be sent by some block in that state. Every target MUST name a declared state.

### 5. Effects

Effects are the only way a chart touches money, identity, the network or message boxes. A wallet MUST refuse a chart that declares an effect kind not listed here, and MUST NOT perform any of these actions for a chart except through a declared effect run from an effect state.

Before running an effect, the wallet resolves every field reference into a concrete action. The approval shows exactly that action, and exactly that action runs.

#### 5.1 Money and items

Each names `coin` and a non-empty `networks` list. Coin ids in this version: `BSV` (Bitcoin SV) and `BTC` (Bitcoin). Networks: `mainnet`, `testnet`. Amounts are integers in the coin's base unit (satoshis for both).

| Kind | Members | Action |
|---|---|---|
| `sendPayment` | `coin`, `networks`, `to` (friend), `amount`, optional `memo` (text) | Pay `amount` to the contact |
| `requestPayment` | `coin`, `networks`, `from` (friend or friends), `amount`, optional `memo` | Send each contact a payment request carrying the user's identity |
| `sendItem` | `coin`, `networks`, `to` (friend), `item` | Transfer the item |

`amount` is `{ field }` naming an amount field whose `coin` equals the effect's, optionally with `divideBy: { countOf, plus? }`: the amount is divided, rounded down, by the number of contacts in the `friends` field `countOf` plus `plus` (0 to 10). A share of zero is an error.

#### 5.2 Identity and network

| Kind | Members | Action |
|---|---|---|
| `signMessage` | `message` (text), `result` (signature) | Sign `Chart app signature\n{id}\n{text}` with the identity key. The prefix keeps the signature from passing as any other challenge. |
| `fetch` | `url`, `result` (fetched) | `GET` one fixed `https` URL with no credentials, no referrer and no redirects. The URL carries no field values, so a chart cannot send data out through it. |

#### 5.3 Message boxes

These reach the user's own message boxes on their BRC-33 host. Wallets declare which boxes charts may reach (§9). A box a wallet uses for its own traffic (device links, settlement, session signalling) SHOULD NOT be offered.

| Kind | Members | Action |
|---|---|---|
| `listMessages` | `boxes`, `result` (messages), optional `blocked` (senders) | List what waits in each box, opened with the user's key and classified, without acting on or acknowledging any of it. Each message carries id, box, sender identity key, a sender name the wallet resolves (contact name, else a short key), time, kind and text. `blocked` receives the wallet's blocked senders. |
| `acknowledgeMessages` | `messages` (selection or message) | Mark handled: BRC-33 `acknowledgeMessage`. The wallet MUST refuse to acknowledge a payment notice it has not yet taken the payment for. |
| `deleteMessages` | `messages` (selection or message) | Clear: BRC-33 `acknowledgeMessage` of any listed message, payment notices included. |
| `blockSender` | `sender` (message or sender) | Add the sender's identity key to the wallet's block list. The wallet clears that sender's messages as they arrive and acts on none of them. |
| `unblockSender` | `sender` (message or sender) | Remove the key from the block list. |

Message kinds: `message`, `payment-request`, `payment-notice`, `tip`, `file`, `identity-card`, `market`, `unreadable`.

### 6. Canonical JSON and hash

The chart hash is SHA-256 over the UTF-8 bytes of the canonical JSON of the chart without its `signature` member. Canonical JSON is RFC 8785 restricted to integers: object members sorted by their names' UTF-16 code units, no insignificant whitespace, strings escaped as JSON.stringify does, integers in plain decimal. The hash is written as 64 lowercase hex characters.

A chart MAY be shared or listed by its hash. A wallet that obtained a chart under a hash MUST refuse it when its hash differs.

### 7. Signature

The author signs the UTF-8 bytes of `chart-app/1\n{hash}` with the private key of `author.identityKey`: ECDSA over secp256k1 with SHA-256 of those bytes as the message digest, DER-encoded, in hex. A wallet MUST refuse a chart whose signature does not verify against `author.identityKey`.

### 8. Verification and approval

Before it shows a chart as runnable, a wallet MUST in order: validate it against §§1–5, check its hash against the one it was shared under (when there is one), verify its signature, and check that it supports every coin, network and box the chart names (§9). A wallet MUST show the chart's declared effects before the app first runs.

`sendPayment`, `requestPayment`, `sendItem`, `signMessage`, `deleteMessages` and `blockSender` need approval. When an effect state with one of these is entered, the wallet resolves the effect and shows an approval drawn by the wallet, never by the chart, that names:

- for payments, the amount with its unit, the coin and network, and the recipient or each contact asked;
- for items, the item and the recipient;
- for signing, the exact text and the app it is signed for;
- for clearing, how many messages, from whom, and how many are payment notices, with a warning that clearing a notice before its payment is taken can lose the payment;
- for blocking, the sender and that their messages, payment notices included, are cleared on arrival.

The approval MUST NOT take keyboard focus when it appears, so no key press meant for an earlier control can approve. Declining runs nothing and goes to `onDecline`. Effects that do not need approval (`fetch`, `listMessages`, `acknowledgeMessages`, `unblockSender`) run on entry; they are still listed before the app first runs.

The status of a payment, request or item transfer a chart starts SHOULD be shown where the wallet shows that kind of activity, on its own entry, and not in app-wide chrome.

### 9. Wallet support

A wallet declares the coins and networks it can run (for example `BSV` on `mainnet`) and the message boxes charts may reach. It MUST refuse a chart that needs any other, naming what is missing. A chart's `networks` list says where it can run; the wallet uses the network of the open account.

## Security considerations

- The chart holds no code. Its reach is the declared effects, each mapped by the wallet to its own code paths and permission checks.
- Field values come only from the user or effect results. A chart cannot write a recipient or an item; it can only preset amounts and text, which the approval shows.
- `fetch` targets are fixed in the signed chart and carry no field values.
- Signing is domain-separated by the `Chart app signature` prefix and the app id.
- A valid signature proves who published a chart, not that it is benign; wallets SHOULD show the author and SHOULD let users keep a list of trusted authors.

## HandCash implementation

This section describes HandCash Desktop only; other wallets implement §§1–9 their own way.

- **Code:** `src/apps/` (types, canonical hash and signature, validator, effect resolution and approval copy, XState runner built from the chart), `src/apps/desktopEffectPorts.ts` (effects on Desktop's wallet calls), `src/components/ChartAppsPanel.tsx` and `ChartAppView.tsx` (renderer), chart `src/machines/chartAppsMachine.ts`.
- **Support:** Bitcoin SV on the network of the open wallet (mainnet or testnet). Message boxes: `inbox` only; Desktop's other boxes carry device links, account moves, swaps and settlement and stay with the wallet.
- **Effects:** `sendPayment` pays a contact's identity key over BRC-29 (`sendBrc29ToIdentityKey`); `sendItem` uses `sendCollectable`; `requestPayment` writes a pay-request message to each contact's thread and delivers it to their message box, with one Activity row per request; `signMessage` signs with the identity key; `listMessages`, `acknowledgeMessages` and `deleteMessages` use `reviewOwnBox` and `clearOwnBoxMessages` in `messageTransport.ts`; `blockSender` and `unblockSender` edit the per-account list in `src/wallet/blockedSenders.ts`, which the inbox poll and direct sessions honour.
- **Built-in suite:** payment request, tip jar, split the bill, send an item and message box, in `src/apps/builtin/`, signed by HandCash's apps key `02a1a56e723281cc9f9b74ab54504b5b6463f2fa910be76d84052698d8b60112f3` and pinned by hash in `hashes.json`. `scripts/sign-app-charts.mjs` re-signs them; `--check` fails when a signature or pin is stale.
- **Where:** Settings → Apps lists each app with its author and verification, shows what it can do, and opens it in place.
