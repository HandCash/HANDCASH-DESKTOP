## Defaults, disabling and current fixes

- Fresh setup/restore applies HandCash history by default (`walletSetupApply.ts`). Explicit `mode: none` clears the backup URL and survives `ensureHandCashServiceDefaults`. Empty history URL makes the BRC-39 URL builder throw before fetch and holder URL resolve to null. **Backup opt-out is real but scoped**; clearing only the URL while mode remains history can be healed back to the default.
- Clearing the diagnostic upload URL is **not opt-out**: `setLogUploadUrl('')` removes the key; the next getter generates a new default bucket. Startup calls the getter/auto uploader independently of history mode. Custom URL redirects collection, not disables it.
- No global service-off guard was found in chainProbeClient, header sources, LTC fallback or scan-login relay. Backup disabled does not prevent these independently triggered requests or diagnostic uploads. This is a code-path result, not a complete device packet-capture result.
- Release-to-current diff is empty for the inspected log/config/history/probe controls and redaction. Current scan-login fixes add typed-code proof, expiry/attempt limits and replay protections; current display fixes bound local reads. These address authentication/performance, **not** diagnostic consent, balance headers, edge logging or metadata linkage. Client changes do not establish any deployed server change.

## Standards versus implementation

[BRC-100](https://raw.githubusercontent.com/bsv-blockchain/BRCs/master/wallet/0100.md), abstract/objectives and foundational requirements, defines a vendor-neutral wallet/app interface, cryptography and permissioned operations. It does not mandate these HandCash endpoints, periodic support uploads, plaintext balance backup headers, persistent log buckets or this holder-record hosting policy. BRC-33 transport and BRC-39 backup are separate functions, not blanket authorization for operator telemetry. Interface identity/linkage operations must remain scoped to their permissions; supporting them is not consent to gateway correlation.

## Minimum remaining work

4. Verify deployed server revisions/configuration, edge invocation fields/IP retention, R2/D1 versions/retention, dashboard/bucket access and deletion. Use synthetic identities and a request capture matrix for fresh install, lock/unlock, idle, refresh, send/failure, crash/restart, account switch and disabled settings, on Desktop and shared Mobile. ## Automatic log follow-up — 6 November 2026

### Release comparison and exact triggers

Compared v1.3.661 with Desktop 83af33f2: `main.tsx`, `logShip.ts`, `logUploadPrefs.ts`, `appLog.ts`, `logFormat.ts`, `diagnosticLog.ts` and `electron/main.ts` are unchanged. Current-source synthetic tests therefore exercise the same inspected implementation, not an installed release binary.

- Before rendering the app, startup attempts a recovered previous-session upload, then starts automatic shipping, including a boot upload. A recovered persisted tail is not proof that the previous run crashed; the uploader does not inspect a crash verdict. Successful upload does not clear the previous-session buffer.
- Five-minute interval and page becoming hidden trigger uploads, subject to a one-minute gap and a single-inflight guard. Send-failure bypasses the time gap, not the inflight guard (`logSpendFailure`, and a collectables failure path). Recovery runs once per process when recovered entries exist. No unlock/consent gate surrounds startup. Manual Settings upload is separate.
- Clearing the upload URL reprovisions a persistent default bucket (80 random bits); it is not an off switch. The bucket survives wallet wipe. Custom bucket syntax validation does not enforce randomness.

### Payload and safeguards

POST is plaintext diagnostic content over the configured HTTP(S) transport; default is HTTPS. Headers identify version, platform and reason. Body header adds upload time, line count and user-agent (140 characters). Body includes up to the renderer's 800-entry ring (4,000 characters per captured entry), recovered persisted tail (normally 350 entries), and for ordinary automatic/manual uploads a deduplicated Electron main tail requested at 96,000 bytes. Recovery-only upload uses renderer/current and previous entries, not the shell tail. Console/error capture and diagnostic producers can contribute origins, amounts/balances, transaction identifiers/outpoints, handles, identity-bearing URLs, timings, lifecycle, stack traces and memory/runtime information. This is not a dedicated vault export, but neither a fixed allowlist of harmless device fields nor anonymized telemetry. The connection exposes IP to the edge; body inclusion and server IP retention are different questions.

New renderer entries pass through `redactAppLogMessage` **before** storage. It pattern-matches `mnemonic`, `rootKeyHex`, `privateKey`, `spendKeyHex`, `password`, `passphrase`, `secret` and `authorization` in supported JSON/key-value forms. Synthetic labelled seed/key markers are removed. This supports a narrow safeguard, **not “keys/seeds cannot be uploaded”**: unlabelled values, other names/encodings or truncated/multiline formats are not comprehensively detected. Restored entries are not re-redacted. Electron IPC reads raw log bytes, and the upload builder does not redact the shell tail or final assembled body. Synthetic persisted/shell markers survived upload interception. The server handler also preserves such markers. No real seed, key or user log was used or found by these tests; they establish a possible path, not an actual secret leak.

### Server source, local demonstration and deployment limit

At BRC-CLOUD be150125, a network-denied in-memory exercise of `handleLogs` accepted 32 synthetic uploads without wallet authentication, retained 30 raw objects, returned their content via bucket-scoped read, accepted bearer deletion of those objects, then returned 404. The handler stores version/platform/reason/time metadata with the raw body, without content redaction. Anyone possessing a bucket has raw read/write/delete access; dashboard sign-in does not protect this separate route. Count pruning is not a time expiry or proof of provider/back-up erasure; the handler lists at most 200 objects per operation.

Additional source finding: `worker.js` calls `notifyLogDashboard` after ingestion if the dashboard binding exists. `logDashboard.js` records bucket activity, queues watched/requested uploads, parses latest/previous logs into facts, and stores facts/digests/verdicts in a Durable Object. Bounds are 300 upload records and 60 facts, not age-based expiry. Configured dashboard operators authenticate with an allowed handle's wallet proof/session; a separate configured reader token permits verdict reads. With a configured Jev key, `askJev` sends a reduced parsed state/error samples to TypeSafe for judgment and emits a verdict to invocation logs. This is conditional source behavior, **not demonstrated production dispatch**, nor necessarily a full raw-log transfer. Raw bucket DELETE has no demonstrated cascade into these derivatives, invocation logs or third-party retention.
